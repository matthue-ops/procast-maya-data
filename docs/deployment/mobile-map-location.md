# Phone map, merchant pin movement and current location

## Approved behavior

Navigation is ordered **Map → Records → Aftersales → Visits** on phone and PC. The default opening section remains Saved Records. On phones (up to 640 CSS pixels wide), Map occupies the available app window above the bottom navigation; the main header and large sync panel are hidden only while Map is active. This does not request browser fullscreen: Chrome's browser bars can remain, while the installed PWA opens without them.

Search stays at the top. Its background is translucent when empty and unfocused, solid when focused or filled. The right-hand menu contains the visit filter (initially All locations), Fit locations, Map settings, Needs correction and My location. A compact status overlay mirrors the existing save/error/offline indicator; tile/library problems remain visible. The permanent record list below the map is removed on all devices. Pins/groups open merchant popups with Open record, Visited today, Move location and Google navigation. Closing a record returns to the same map. Needs correction opens a searchable, temporary dialog for missing/invalid coordinates and invalid/future visit dates; opening a record closes that dialog first.

PC keeps its existing map/header layout, with the reordered navigation and added pin/current-location controls. Resizing moves the single navigation element between its phone and desktop positions inside the app, retaining existing inert and modal protections.

## Merchant location edits and database integrity

Tap one merchant's pin → Move location → drag the preview marker → Save location or Cancel move. For numbered groups, choose the individual merchant first. Other pins are locked during the preview. Search, settings, fitting, correction selection and GPS start/stop controls are locked until the move ends. Keyboard users can move the preview with arrow keys. Starting a merchant move stops the separate GPS display to avoid confusing the two markers.

Dragging, cancelling, opening a popup and GPS updates make no business-data write. Saving an unmoved pin preserves the exact original coordinate string, including its precision. A moved position is validated as latitude/longitude, normalized for longitude wrap when necessary, and formatted to seven decimal places (roughly centimeter precision, not a claim of sensor accuracy).

Save checks that the merchant still exists, that the configured coordinate field is still the same text field, and that its current local value matches the preview's original value. It changes only that record's coordinate field. LAST VISIT, notes, other merchants (including merchants sharing the original coordinates) and Excel datasets are not changed. Stored merchant/Google Maps link fields are not rewritten; if they encode an old location, review them separately. Navigation generated by the map uses the newly saved coordinates. Moving a Procast pin does not edit a place on Google's own maps.

This uses the existing Saved Records single-field diff, durable IndexedDB outbox, UUID retries, server generations/tombstones, and change history. **No new SQL, tables, schema, grants or environment variables are required.** Accepted merchant coordinate edits remain in the existing business-record recovery history; that history is separate from your personal GPS position, which is never written. Same-field edits from different devices retain the existing server-acceptance ordering; this does not add geographic conflict resolution.

An unsaved pin preview stays in memory and blocks automatic cloud adoption/PWA update reloads. Leaving Map asks whether to discard it; cancel keeps the recorded coordinates, and a close/reload warns if a preview remains. The view cannot be left while the local save is in progress. Committed offline coordinates survive reload and sync on reconnection while the app is open. If local storage fails, the existing error indicator and map message tell you to keep the app open and download a Saved Records backup under Records → Options; do not clear site data. A storage failure is not presented as a successful durable save.

## Your phone's current location — no application history

My location explicitly requests browser geolocation permission over HTTPS (loopback is permitted for local tests). It shows a blue dot and a meter-based accuracy circle, centers on the first fresh fix, and updates the dot as fixes arrive without repeatedly moving a manually explored view. The GPS dot cannot be dragged or used to overwrite a merchant. No map API key, Google Maps Platform service or paid geolocation API is introduced; normal mobile-data/provider limits still apply.

Only the current display exists in memory. There is no GPS history collection, telemetry, localStorage/IndexedDB entry, sync action, export or backup field for it. Stop my location clears the watch/dot/accuracy circle. Leaving Map, hiding/backgrounding the page, permission/error/timeout, and page exit clear it as well. Returning to Map does not restart it automatically. Old callbacks cannot restore a stopped marker. Old/invalid readings are hidden; a last fix expires after 30 seconds without a fresh update. The viewport can remain on the last viewed area, but no trail or coordinate history is retained.

The browser/OS supplies location and may use its own location services. Centering on your location requests ordinary map tiles from the existing OpenStreetMap provider, revealing the viewed tile area and normal browser request metadata to that provider. The app's service worker still never caches map tiles or GPS data; ordinary browser/provider caching remains outside application history. Offline GPS availability/accuracy depends on the phone and browser, and new map backgrounds require internet. No background tracking after the app closes is added.

## Deployment, backups and rollback

The PWA build command/output remain `node scripts/build-pages.mjs` and `dist`. Regenerate the committed offline stylesheet after index changes with `node scripts/compile-pwa-styles.mjs` (or set MAYA_TAILWIND_CLI to an installed Tailwind 3.4.17 CLI). The generated worker hashes the revised HTML/JS/CSS together; installed devices receive the existing guarded update flow.

Before promotion, sync/export device backups and verify the coordinate field binding. Review the PR against `deploy/cloudflare-pages`; no SQL migration should be run for this feature. After deployment, test the installed app on the physical phone: full-window layout, menu/search, a cancel, one deliberate coordinate save, offline reload/reconnect, permission allow/deny and stopping/backgrounding GPS. Chromium tests use emulated locations, not physical satellite hardware. Actual live Supabase/tile availability and device GPS precision were not tested from the restricted development environment.

A frontend revert to the previous PWA-capable commit removes these controls after its normal worker update; it does not restore coordinates that were deliberately saved. Recover incorrect merchant coordinates from a backup or existing private change history, or explicitly edit them back. Do not clear site data, uninstall with pending entries, or use unrelated SQL rollback scripts. Retiring the PWA worker entirely still requires the coordinated network-only rollback documented in installable-app.md.

## Isolated validation

`tests/mobile-map-browser.cjs` serves the built app locally, intercepts all external requests with synthetic RPCs/tiles, and tests actual touch dragging, no-op Save precision, Cancel/discard, a coordinate-only offline queue and reload/reconnect, popup/group selection, missing-coordinate access, phone/desktop layouts, permission/stale/error/hidden cleanup, no GPS data in record storage, and the browser's real geolocation API with an emulated position. Existing workspace database/browser, pure model/Excel, build and real PWA update/rollback suites cover their unchanged behaviors. No live database writes or production deployment are part of development validation.
